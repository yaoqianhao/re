## D1 物理端口 trait 化的边界

- 问题：`AI_ROADMAP §3.3` 把「`rapier` 是否转默认 feature」列为 M0 顺延到 M2 的待决策项。A03 做 trait 化时，是否同期把 `rapier` 变默认后端？
- 选项：
  - **A（建议）**：只做抽象层（capsule / raycast / heightfield 查询三组 trait），`rapier` 维持可选 feature，默认仍 builtin。风险最低，项 1–6 的物理需求 builtin 全部够用。
  - B：同期把 `rapier` 转默认 feature。好处是碰撞质量立刻提升；代价是 `dep_debt`/`size_debt` 双线波动，且 C04 地形碰撞要在两套后端各验一遍。
- 影响：选 B 则 A03 工作量约翻倍，且 C04/G 阶段每张判据卡都要双后端跑一次。
- 拍板结论：`待填`

## D2 角色控制器落位

- 问题：角色控制器是 core 能力还是独立 crate。
- 选项：
  - **A（建议）**：`r3e-core/src/character/`。与 `Scene`/`Transform` 同 crate，避免新增跨层依赖边（`dep_debt` 已顶格）。
  - B：新建 `r3e-character` crate。隔离更彻底，但 `r3e-script` 要调用它就得加依赖边 → `dep-check` 立刻红。
- 影响：选 B 必须先偿还 `dep_debt`（即 D13 改为「M2 内偿还」），卡序要重排。
- 拍板结论：`待填`

## D3 角色命令命名空间

- 问题：控制器的命令与能力用什么前缀。
- 选项：**A（建议）`character.*`**；B `player.*`。
- 影响：进入 `capabilities.json` 后改名属破坏性变更，越早定越好。引擎层不应认识「玩家」概念，故建议 A。
- 拍板结论：`待填`

## D4 NavMesh 烘焙时机

- 问题：导航网格何时生成。
- 选项：
  - **A（建议）**：编辑期/CLI 预烘焙，产物随场景文件缓存，运行期只加载。确定性好，判据可复现。
  - B：运行期即时烘焙。改地形即生效，但烘焙耗时进帧预算，且同输入不同时序可能产出不同网格，与项 3 判据冲突。
- 影响：选 B 需在 G04 帧尖峰判据里额外给烘焙留预算。
- 拍板结论：`待填`

## D5 导航判据采样口径

- 问题：「路径长度 ≤ 直线 1.6 倍」怎么采样。
- 选项：**默认**：固定 20 组起终点（seed 42，含绕障/开阔/不可达三类），逐组断言；不可达组断言返回失败码。
- 影响：组数决定 D05 测试量；阈值 1.6 建议不改（roadmap 原文）。
- 拍板结论：`待填`

## D6 Prefab 覆盖存储格式

- 问题：实例覆盖字段怎么存。
- 选项：**A（建议）** diff 补丁（只存与模板不同的字段）；B 完整快照。
- 影响：项 4 判据「覆盖字段只存差异」直接排除了 B。此条实际只需确认，无争议。
- 拍板结论：`待填`

## D7 Prefab 与 Scene 的关系

- 问题：实例表放场景内还是独立 prefab 库。
- 选项：
  - **A（建议）**：Scene 内嵌实例表，模板按 ID 引用外部 prefab 文件。序列化简单，与 G 阶段分块流式兼容（块只带实例引用）。
  - B：全部内嵌到场景文件。单文件自包含，但 100 实例会显著撑大场景文件，且模板改动无法批量生效。
- 影响：影响 E 阶段数据结构与 G 阶段块划分。
- 拍板结论：`待填`

## D9 根运动与 IK 叠加顺序

- 拍板结论：`待填`

## D10 流式分块尺寸与驻留策略

- 问题：200×200 米地形如何切块、驻留几块。
- 选项：**默认** 50 米分块 → 4×4 = 16 块；驻留 3×3（9 块），预取 1 圈。
- 影响：块越小切换越频繁（帧尖峰判据越难），越大则单块加载越重。50 米是权衡点，可按实测在 G04 微调。
