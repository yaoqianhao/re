# 提案：插件写侧能力槽位（提交给 ai_ide）

- 提案方：`rust3d-engine` / `r3e-plugin`（M1-S1-D 能力名裁决的后续）
- 提交对象：`D:\ai_ide` 插件系统（P5 之后的能力模型演进）
- 状态：**提案，未采纳不影响本仓**。本仓按「形态 1」先行结项，见 §5
- 日期：2026-11-19

---

## 1. 提案要解决什么

`rust3d-engine` 插件在 M1 期只做只读工具（5 个工具全 `risk=read`，能力声明 `["fs.read"]`）。M2 起要做写侧：**场景写入**与**文档事务**（`tx.begin/apply/preview/commit/rollback` 那条链路，M1-S1 已在引擎侧落地）。

原计划是在清单里声明两个业务能力名 `scene.write` / `doc.transaction`，由 ai_ide 宿主认领。核查后发现这个计划在 ai_ide v1.0 的能力模型里**没有落点**，本提案给出三条可选形态与推荐路线。

## 2. 现状实证（ai_ide 侧，2026-11-19 读取）

| 事实 | 证据 |
|---|---|
| 能力表封闭，共 7 项：`fs.read` / `fs.write` / `search` / `workspace.info` / `progress` / `net.fetch` / `llm.chat` | `crates/plugin/src/manifest.rs:63-71` `ALLOWED_CAPABILITIES` |
| 表外能力**直接拒载**，不是"暂不支持" | `manifest.rs:549`「未知能力 {cap}；host 只提供 {}」 |
| 能力名是**闸门键**，运行期由 `capability_of(method)` 唯一映射；`None` 的方法回 `-32601` | `crates/core/src/plugin_host.rs:122` |
| 每一项能力都挂着真实 `host/*` 方法 | `crates/plugin/src/host_api.rs`：`host/log`、`host/progress`、`host/view.refresh`、`host/net.fetch`、`host/llm.chat` + fs 五件套 |
| 写侧安全口径 = 能力 `fs.write` + **逐文件审批**（`scope_key` = 规范化路径）+ `path_field` 闸门 | `docs/14-插件系统设计.md` §7.1 / §8.1 |

结论：`scene.write` / `doc.transaction` 这类**业务语义能力名**在 v1.0 里既无方法可挂、也无审批口径可套。硬加进白名单的结果是——授权页多两个勾选项，勾了也不产生任何闸门，与 `manifest.rs:105` 那段注释的立表初衷（"未知能力无法被闸门覆盖，比直接拒载更危险"）正好相反。

## 3. 三种可选形态

### 形态 1：不新增能力名，写侧走 `fs.write` + `risk=write`（最小改动）

- 插件声明 `["fs.read", "fs.write"]`；写侧工具 `risk="write"` 且给 `path_field`。
- 所谓"场景写入" = 对 `.json` 场景文件的原子写；"事务"由**插件自行维护**（引擎侧已有 `tx.*`，宿主不介入）。
- 宿主完全不用改。

| 维度 | 评价 |
|---|---|
| 改动面 | 零（ai_ide 不动） |
| 审批粒度 | 按文件，天然正确 |
| 审计 | 复用既有写审计行 |
| 短板 | 一次事务触达 N 个文件 → 用户被问 N 次；跨文件原子性无宿主保证 |

### 形态 2：宿主新增通用批量事务槽 `host/tx.run` + 能力 `tx.run`（推荐在 v1.x 评估）

让宿主提供**与业务无关**的批量写原语，插件提交一组操作，宿主负责原子性、一次审批、一行审计。宿主不需要认识"场景"或"文档"，只需要认识"一组文件写操作"。

契约草案：

```jsonc
// 请求
{ "method": "host/tx.run",
  "params": { "ops": [ { "path": "a.json", "content": "...", "encoding": "utf8" },
                       { "path": "b.json", "content": "..." } ],
              "message": "AI 场景事务：3 个文件" } }

// 成功回包
{ "committed": true,
  "applied": [ { "path": "a.json", "bytes": 1204, "sha256": "..." } ],
  "scopeKey": "tx:2026-11-19T12:00:00Z" }
```

闸门顺序（沿用 §8.1 五段式，只在"路径"与"审批"两段改为批次语义）：

1. **能力**：`tx.run` 未授权 → `6103`；
2. **路径**：逐条过路径闸门，**任一条越界整批拒，不部分执行**（部分执行等于把用户拖进半完成状态）；
3. **参数**：累计 `content` 计入单帧 1 MiB 预算，超限按 `-32602` 拒，不截断；
4. **审批**：一批**只问一次**，`scope_key = 批次哈希`；用户拒绝 → 零写入；
5. **配额**：按批次数计，不按文件数。

原子性：全部落 staging → 逐条 `rename`；中途失败回滚已 rename 的条目，回包带 `rollbackErrors`（best-effort 但必须可见，不许静默）。

验收判据（建议同时进 ai_ide 的测试）：

- 一条路径越界 → 整批零写入；
- 审批被拒 → 零写入（不能出现"拒了但写了第一条"）；
- 第 2 条 `rename` 失败 → 回包 `committed:false` 且 `rollbackErrors` 非空，第 1 条已回滚；
- 累计内容超 1 MiB → `-32602`，不裁半截落盘。

| 维度 | 评价 |
|---|---|
| 改动面 | 宿主新增 1 个方法 + 1 个能力名 + 审批 UI 一处文案 + 审计 1 个 kind |
| 审批粒度 | 按事务，一次打扰 |
| 短板 | 宿主多了"事务"概念；需要处理回滚的半成功态 |

### 形态 3：给插件域开二级命名空间（不推荐）

如 `plugin.rust3d-engine.scene.write`，宿主只做"用户点没点同意"的存储与审计，闸门逻辑交给插件自查。

不推荐的理由：这等于把安全判断委托给被审查方。`manifest.rs:105` 立表时明确否掉过这条路，回到它等于把 v1.0 的能力模型拆掉。只有在"宿主完全不可能介入"时才值得考虑，本场景不满足这个前提。

## 4. 推荐路线

| 阶段 | 动作 |
|---|---|
| M1（现在） | r3e 侧按**形态 1** 结项：能力名保持 `["fs.read"]`，写侧工具上线时才加 `fs.write`；两个业务能力名从 r3e 正式撤销 |
| M2 开工前 | 评估**形态 2**：把"批量事务审批"做成 ai_ide 的**独立特性**（对任何插件都有用），而不是给 3D 引擎开特例 |
| 触发条件 | 出现"一次意图触达 ≥3 个文件"或"跨文件原子性成为硬需求"时，形态 1 即到瓶颈，转形态 2 |

## 5. 本仓的先行结项（不依赖本提案是否被采纳）

- `r3e-plugin/src/spec.rs::CAPABILITIES` 维持 `["fs.read"]`，**不再预留** `scene.write` / `doc.transaction`；
- 裁决依据与迁移口见 `docs/m1/M1_S1D_SUBSTITUTION.md` §8；
- 若形态 2 落地，本仓只需把写侧能力声明从 `fs.write` 换成 `tx.run`，插件侧代码不动（引擎侧的 `tx.*` 本来就是协议面方法，与宿主能力无关）。
