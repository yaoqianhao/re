# rust3d-engine：以 AI 为核心的解耦开发路线图

- 制定日期：2026-11-14
- 现状基线：9 crate / 158 源文件 / 约 6.9 万代码行 / 90 套件 1335 测试全绿 / 0 告警
- 现状定位：**内核可用，游戏不可用；可编程，不可让 AI 写**

---

## 一、先立四个判断（路线图的全部依据）

### 判断 1：当前缺的不是功能，是「AI 参与权」

引擎有 364 个脚本函数、24 个 RPC 方法、能力已全面协议化——**这些都是只读或半只读的**。`r3e-plugin` 能力声明只有 `fs.read`，AI 能看不能改。同时场景没有单一权威状态、没有事务、没有 undo。

结论：**先补参与权，再补功能**。继续堆渲染特性只会拉大"AI 能看懂但改不动"的落差。

### 判断 2：AI 为核心的真正瓶颈是「验证成本」，不是「生成能力」

AI 写代码快，但没人能低成本判断它写对没有。当前验证路径是：改代码 → 编译 → 起 GPU → 肉眼看画面。这条路对 AI 是死路。

反推设计目标：**任何改动都必须有一条不需要 GPU、不需要人眼、可以自动判定对错的路径。**

这一条决定了：可验证性基建必须前置到 M0，不能留到"以后再补测试"。

### 判断 3：解耦对 AI 的价值是「可增量」，不是「好看」

| 单体现状 | 对 AI 的具体伤害 |
|---|---|
| `renderer.rs` 5,582 行（M0-S1 已拆为 `renderer/` 17 个模块，最大 716 行） | AI 读一次吃满上下文窗口，读不全就改错 |
| `api.rs` 3386 行 | 加一个脚本函数要扫全文件，容易破坏已有 364 个函数 |
| `app/editor.rs` 3234 行 | 改 RPC 和改主循环挤在一起，语义边界模糊 |
| `r3e-app` 混三件事 | 想跑 headless 测试就必须把窗口也拖进来 |

解耦的真实收益是三条：**可增量读、可并行改、可局部验**。这三个是 AI 协作的前提，不是工程洁癖。

### 判断 4：不要为 AI 另造一套接口

AI 和未来的编辑器 UI 必须走**同一条命令通道**。否则两套语义必然漂移，届时修 bug 要修两遍，且 AI 那套永远落后于 UI 那套。

推论：**权威模型在引擎内，AI 在引擎外。** AI 只是一个"客户端"，和 UI 平级。

---

## 二、目标架构：五层 + 三条正交链

```
┌─ L4 表达层 ─────────────────────────────────────────────┐
│  编辑器 UI(未来)   CLI/AI Agent   测试脚本   CI 校验器   │
└──────────────────────┬──────────────────────────────────┘
                       │ 只允许走协议，禁止直接 use 引擎类型
┌─ L3 协议层 r3e-protocol ────────────────────────────────┐
│  JSON-RPC 消息  机器可读能力清单  事务/意图  错误语义    │
│  依赖：仅 serde。禁止依赖 core/physics/任何引擎类型      │
└──────────────────────┬──────────────────────────────────┘
┌─ L2 编辑权威层 r3e-doc ─────────────────────────────────┐
│  Document(唯一真值) → Command → Transaction → UndoStack │
│  Validator(不变量校验)  Diff/Patch  语义查询 WorldQuery  │
│  依赖：仅 core 的数据结构。禁止依赖 render/physics/audio │
└──────────────────────┬──────────────────────────────────┘
┌─ L1 领域层（端口-适配器）───────────────────────────────┐
│ core | render | physics | audio | asset | anim | nav     │
│ terrain | char | flow  —— 各自出 trait 端口，互相不直连 │
└──────────────────────┬──────────────────────────────────┘
┌─ L0 平台层（可替换适配器）──────────────────────────────┐
│ wgpu | winit | rapier | rodio | ufbx/gltf               │
└─────────────────────────────────────────────────────────┘

三条正交链（贯穿每一层，不是某一层的功能）：
  ① 可观测：结构化日志 / 性能计数器 / 状态快照
  ② 可验证：CPU 不变量校验 / headless 确定性回放 / 像素回归
  ③ 可回滚：事务边界 / undo 栈 / diff-patch
```

### 2.1 crate 目标布局（9 → 13）

| crate | 状态 | 职责 | 关键约束 |
|---|---|---|---|
| `r3e-core` | 保持，内部拆分 | 纯数据与算法：场景图、动画、材质、UI 数据 | 零图形/物理依赖（现状已达成，保持） |
| `r3e-render` | 保持，`renderer.rs` 已拆为 `renderer/`（M0-S1） | wgpu 后端 + gfx 抽象 | 唯一持有 GPU 句柄的层 |
| `r3e-physics` | 保持 | 物理端口 + rapier 适配器 | 端口 trait 化，`rapier` feature 默认开启 |
| `r3e-audio` | 保持 | 音频端口 + rodio 适配器 | 后续加总线/混音器 |
| `r3e-asset` | 保持 | 导入管线 | 不依赖 render（现状正确） |
| `r3e-script` | **改造** | rhai 绑定 | 只能经 `CapabilityHost` trait 注入能力，**禁止 `use r3e_physics::*`** |
| `r3e-protocol` | **新（由 editor 演进）** | 协议 + 能力清单 + 事务消息 | **仅 serde**，零引擎类型 |
| `r3e-doc` | **新** | Document/Command/Transaction/Undo/Validator | **本路线图的核心新增** |
| `r3e-runtime` | **新（由 app 拆出）** | 窗口、主循环、时间步、headless 模式 | 不含任何 RPC |
| `r3e-editor-host` | **新（由 app 拆出）** | RPC 服务端，桥接 protocol ↔ doc | 不含主循环 |
| `r3e-game` | **新** | 游戏层框架：玩家、交互、关卡流程 | 示例游戏的宿主，验证"引擎真的能做游戏" |
| `r3e-nav` | M2 新增 | NavMesh 生成 + A* 查询 | 独立 crate，不依赖渲染 |
| `r3e-terrain` | M2 新增 | 高度图地形 + 分块 + 材质混合 | 独立 crate |
| `r3e-plugin` | **重写** | AI 外部工具进程 | **只依赖 protocol**，零 core/physics 依赖 |

### 2.2 依赖规则表（CI 强制，违反即红）

| 来源 | 允许依赖 | 明确禁止 |
|---|---|---|
| `core` | glam, serde, bytemuck, fontdue | 任何 GPU/物理/脚本/窗口库 |
| `doc` | `core` | `render`, `physics`, `audio`, `rhai` |
| `protocol` | serde | **一切引擎 crate**（含 `core`） |
| `render/physics/audio/asset` | `core` + 各自平台库 | 互相依赖 |
| `script` | `doc`, `protocol` + trait 端口 | 直接依赖具体子系统的类型 |
| `runtime` | 下层全部 + `doc` | `protocol`（运行时不需要懂 RPC） |
| `editor-host` | `protocol`, `doc`, `runtime` | `render` 内部实现细节 |
| `plugin` | `protocol` | 引擎所有其他 crate |
| `game` | 下层全部 + `doc` | `protocol`, `editor-host` |

落地方式：`cargo xtask dep-check` 解析依赖图对照上表，进 CI 第一道门（比 clippy 更快失败）。

## 三、路线图：M0 → M4

总体原则：**每个里程碑都必须产出一个"AI 能验证的产物"**，否则不算完成。

---

### M0：解耦止血 + 可验证地基（地基期，约 4–6 周）

**为什么要先做**：不拆 `r3e-app`、不引入权威文档模型，后面所有 AI 能力都建在流沙上。M0 不加任何用户可见功能，全部是结构性投入。

**交付物**

| # | 内容 | 验收标准（可自动判定） |
|---|---|---|
| M0-1 | 拆 `r3e-app` → `r3e-runtime` + `r3e-editor-host` + `main` 薄壳 | 三个 crate 各自可独立测试；`runtime` 能在无窗口 headless 下跑 600 帧 |
| M0-2 | 拆三个单体文件（`renderer.rs` / `api.rs` / `editor.rs`）到 ≤800 行/文件 —— `renderer.rs` 已完成（M0-S1，2026-11-15，17 文件最大 716 行）；`editor.rs` 随 M0-S0 的 crate 拆分消解；`api.rs`（4,070）待做 | 单文件行数 CI 门禁；拆分后测试数不减（≥1335） |
| M0-3 | 新建 `r3e-doc`：Document 模型接管场景唯一真值 | `core::scene` 不再被 `app` 直接可变借用，只能经 `doc` |
| M0-4 | Command + Transaction + UndoStack 落地 | 任意命令序列 apply 后 `undo` 全量回退，状态哈希与初始一致 |
| M0-5 | `r3e-protocol` 从 `r3e-editor` 剥离，零引擎依赖 | `cargo tree -p r3e-protocol` 只有 serde |
| M0-6 | 能力清单自动生成：`capabilities.json` 由代码导出，非手写 | 清单与实现不一致 → CI 失败 |
| M0-7 | Headless 确定性回放框架 | 同输入两次运行，帧状态哈希完全相同 |
| M0-8 | CPU 侧不变量校验器 v0（场景/材质/动画数据合法性） | 故意注入非法场景 → 校验器必须报错，有测试守护 |
| M0-9 | `dep-check` 依赖门禁进 CI | 故意加一条违规依赖 → CI 红 |

**crate 变化**：+`r3e-doc` `r3e-protocol` `r3e-runtime` `r3e-editor-host`；`r3e-app` 收缩为壳；`r3e-editor` 保留为兼容别名或废弃。

**M0 退出条件**：AI 可以在改完代码后，只跑 `cargo xtask verify`（fmt + dep-check + test + headless replay + 不变量校验）就判断是否改对，全程不起 GPU。**这一条不达成，不进 M1。**

---

### M1：AI 写入闭环（核心期，约 4–6 周）

**目标**：让 AI 从"看"变成"改"，并且改得可回滚、可解释、可验证。

**交付物**

| # | 内容 | 验收标准 |
|---|---|---|
| M1-1 | 事务协议：`tx.begin / tx.apply / tx.preview / tx.commit / tx.rollback` | 任意 AI 事务 dry-run 返回结构化 diff，commit 前零副作用 |
| M1-2 | `r3e-plugin` 重写：读写能力 + 只依赖 protocol | 插件二进制不链 core/physics；能力声明含 `scene.write` `doc.transaction` |
| M1-3 | 语义查询 `WorldQuery`：按类型/标签/包围盒/组件过滤，返回语义化结果 | AI 不需读原始 JSON 就能回答"这个场景里有哪些可交互物" |
| M1-4 | 高层意图命令：`spawn_prefab` `paint_terrain` `place_light` 等，内部展开为 Command 序列 | 一条意图命令 = N 条原子命令，undo 一次全退 |
| M1-5 | 内容验证器：可通行性、悬空、穿模、材质缺失、引用断裂 | 故意生成不可达关卡 → 验证器给出具体失败点位 |
| M1-6 | `r3e-cli`：`tx` / `query` / `verify` / `replay` 子命令 | 全流程可脚本化，无交互 |
| M1-7 | 变更半径报告：一次事务列出受影响的对象、材质、依赖 | 事务输出含 `impact` 字段 |
| M1-8 | AI 工作流文档 + 三个可复现的 AI 任务范式 | 三个范式从零跑通，命令可复制粘贴 |

**M1 退出条件**：一个 AI Agent（不修改引擎代码）能仅通过 `r3e-cli` + 协议，完成"生成一座可通行的小场景、验证、失败则回滚重试"的完整闭环。

---

### M2：游戏可用最小集（结构期，约 6–8 周）

**目标**：补齐 RPG/沙盒的结构性缺口。没有这些，"做游戏"无从谈起。

按依赖顺序（不能并行，后项依赖前项）：

| 序 | 内容 | 为什么必须在这个位置 |
|---|---|---|
| 1 | **角色控制器**（胶囊、台阶、斜坡、地面吸附） | 一切"玩家能走"的前提；依赖已完成的物理端口 |
| 2 | **地形系统**（高度图、分块流式、材质混合、碰撞） | 沙盒地基；产出地形才能验角色控制器 |
| 3 | **NavMesh + A\*** | NPC 寻路；需要地形与角色参数作为输入 |
| 4 | **Prefab / 实例化 + 覆盖** | AI 生成内容的最小复用单位；无此则每次生成都是全量复制 |
| 5 | **IK + 根运动 + 动画事件** | 角色表现力与判定框；动画事件是战斗系统前提 |
| 6 | **场景流式加载（分块 + 异步）** | 开放世界门槛 |
| 7 | **`r3e-game` 首个垂直切片**：可走、可交互、有 NPC、有任务 | 验证"引擎真的能出游戏" |

**M2 退出条件**：`r3e-game` 里一个 200×200 米地形场景，玩家可自由行走、NPC 能寻路追击、帧率在目标硬件上稳定 60fps，且**全部可由 CLI 生成与验证**。

---

### M3：内容管线 AI 化（产能期，约 6–8 周）

**目标**：让 AI 能生产内容，而不只是操作场景。这是"开发游戏也以 AI 为核心"的实质。

| # | 内容 | 说明 |
|---|---|---|
| M3-1 | 资产管线正式化：导入 → 校验 → 引用完整性 → 增量重建 | 现在 `r3e-asset` 有导入能力，但缺引用图与增量 |
| M3-2 | `r3e-flow`：对话树 / 任务 / 状态机，**纯数据驱动** | 数据格式即 AI 的产出格式，AI 生成对话不需要写代码 |
| M3-3 | 数据 Schema 化 + 自动校验 + 从 schema 反向生成 AI 提示 | AI 产出内容前先拿到约束，降低无效生成 |
| M3-4 | 关卡生成器接口：程序化 + AI 混合，带种子与可复现 | 同种子必然同结果，便于回归 |
| M3-5 | 平衡性/可玩性模拟器：headless 跑 N 次自动对局 / 路径模拟 | 给 AI 提供量化反馈信号，而不是"看起来还行" |
| M3-6 | `r3e-cli content` 子命令族：生成/校验/预览/差异 | AI 内容生产全链路可脚本化 |
| M3-7 | 资产内容寻址 + prefab 引用替换 | 避免 AI 生成导致资产爆炸式重复 |

**M3 退出条件**：AI 仅凭自然语言需求 + schema，产出"一段对话 + 一个任务 + 一个关卡块"，并自动通过校验与可玩性模拟，人工只做审美判断。

---

### M4：工业化（打磨期，持续）

按性价比排序，不做承诺式排期：

| 优先 | 内容 | 理由 |
|---|---|---|
| 高 | TAA + 运动模糊 | 路线表唯一"未开始"项，且是画面完成度分水岭 |
| 高 | 音频总线 + 混音 + 动态音乐 | 现在只能"播空间音"，做不出游戏音频设计 |
| 高 | 编辑器 UI（`egui` 或 Web 前端，走现有协议） | 人类介入 AI 产出的必要界面；协议已就位，成本已摊薄 |
| 中 | 第二图形后端（Vulkan/DX12） | 验证 gfx 抽象是否真不泄漏；建议**只做 Vulkan**，别摊薄 |
| 中 | 性能体系：多线程渲染、动态分辨率、性能分层预设 | 沙盒场景必然撞性能墙 |
| 中 | OIT 半透明 / 金属度贴图 / 多 UV | 美术产能的实际约束 |
| 低 | Ragdoll / 软体 / 流体 | 加分项，非门槛 |
| 低 | 网络同步 | 单机 RPG 不需要；要做联机再单独立项 |

**M4 原则**：M4 的每一项都应该由"游戏实际卡住了"来驱动，而不是由功能清单驱动。**先做出一个能玩的东西，再让它变好。**

## 四、"AI 为核心"的六个具体机制

路线图不是口号，需要落到机制上。以下六条是本路线图区别于"普通引擎路线图"的地方。

### 机制 1：能力自描述（机器可读，不手写）

```
cargo xtask gen-capabilities  →  capabilities.json
{
  "version": "1.0",
  "commands": [{ "name": "scene.spawn", "params_schema": {...},
                 "reversible": true, "cost": "low", "since": "M0" }],
  "invariants": [...],
  "unsupported": [...]   // 明确列出"不支持"，供 AI 探测降级
}
```

关键：**由代码导出，不是文档手写**。清单与实现不一致，CI 直接红。`unsupported` 字段继承现有 `-32601` 的诚实文化——让 AI 能可靠区分"没这个能力"和"执行失败"。

### 机制 2：事务优先，AI 永不直接改状态

```
AI 意图 → tx.preview(dry-run) → 得到 diff + impact → 自检 → tx.commit | tx.rollback
```

AI 不允许直接 mutate 场景。所有写入必须经 `r3e-doc` 的 Transaction，天然带 undo 边界。这一条同时解决三个问题：可回滚、可审查、可并行（不同事务冲突可检测）。

### 机制 3：语义查询代替原始数据读取

不要给 AI 364 个函数 + 一堆 JSON。给它：

```rust
world.query(Query { kind: Interactable, in_bbox: bbox, has_component: "trigger" })
  → [{ id, name, tag: ["rpg","chest"], pos, interact_radius }]
```

粗粒度、意图化、稳定。AI 处理语义对象，不处理内存布局。

### 机制 4：三层验证，逐层加价

| 层 | 手段 | 成本 | AI 可自主跑 |
|---|---|---|---|
| V1 | 编译 + 单元/契约测试 | 秒级 | ✅ |
| V2 | headless 确定性回放 + 不变量校验 + 内容验证器 | 十秒级 | ✅ |
| V3 | 像素回归 / 人工审美 | 分钟级 + GPU | ❌（只做最终确认） |

**设计红线**：任何新功能，若无法在 V1/V2 层判定其对错，则该功能设计不合格，打回重设计。这条红线是"AI 为核心"能否成立的唯一硬保障。

### 机制 5：确定性是一等公民

固定时间步、可设种子、可控帧率、状态可哈希。缺了这条，AI 无法重现 bug、无法回归、无法自检。当前引擎已有视觉回归和契约测试基础，需把**确定性**从"测试技巧"升级为"引擎约束"。

### 机制 6：AI 开发引擎自身的工作流

| 环节 | 机制 |
|---|---|
| 上下文控制 | 单文件 ≤800 行硬门禁，保证 AI 一次读全 |
| 改动边界 | 依赖门禁 + 每 crate 独立可测，AI 改动影响面可预测 |
| 并行开发 | crate 级隔离，允许多个 AI Agent 同时改不同 crate |
| 反馈闭环 | `cargo xtask verify` 一条命令覆盖全部 V1/V2 |
| 契约守护 | 每个 crate 出端口 trait，改实现不破契约；契约测试由 AI 补写 |

## 五、必须避免的五个反模式

| 反模式 | 为什么是坑 | 正确做法 |
|---|---|---|
| 在 `r3e-app` 里直接塞 AI 逻辑 | 引擎被 AI 供应商绑定，换模型要重写，且 AI 错误会污染主循环 | AI 永远在进程外，只经 protocol |
| 给 AI 一堆细粒度 RPC 让它自由编排 | 编排逻辑散落在提示词里，不可复现、不可回滚、每次结果不同 | 高层意图命令 + 引擎内展开为原子命令 |
| 先用自然语言提示词驱动，再补验证 | 验证缺失时 AI 的产出无法判断，会积压成技术债 | 验证先于生成（M0 先于 M1） |
| 为 AI 单开一套"简化接口" | 两套语义必然漂移，AI 那套永远落后 | AI 与 UI 共用同一条命令通道 |
| 功能清单驱动 M4 | 做了一堆没人用的特性，游戏还是不好玩 | 由"做游戏时实际卡住"驱动 |

## 七、立即可执行的第一步

不要等"想清楚整个路线"。M0 里有一件事可以**本周就做**，且能立刻缓解最大痛点：

> **拆 `r3e-app` 为 `r3e-runtime` + `r3e-editor-host`。**

理由：它是当前解耦最薄弱处（一个 crate 混三件事），也是 AI 接入时最容易污染的地方。拆完之后 headless 模式天然可行，后续所有验证基建才有落脚点。

第二件：**`renderer.rs` 5,582 行拆分**（M0-S1，已完成：17 个文件最大 716 行，拆分后测试数 1,343 不减）。理由同上——AI 读不全就改不对，这是可度量的直接障碍。
